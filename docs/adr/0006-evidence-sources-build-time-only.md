# 外部資料只用來事先整理成表，系統評估時不呼叫

> 設計決策的參考紀錄，不是硬性規定；想調整請見 [README](README.md)。

藥物交互作用的研究盤點了七個外部來源（TFDA、SUPP.AI、NIH ODS、NCCIH、DailyMed、openFDA、DDInter），
並提出另一種流程：每次評估都即時查 SUPP.AI 候選交互作用，再蒐集多源證據、整合、交給規則引擎算風險。

我們決定**這些來源只拿來事先整理資料**：負責組員依建表規範查閱它們，
把通過審核的交互作用寫成規則表的一列，並綁定出處。系統評估時只查規則表，不呼叫任何外部來源。
這與 `docs/prd.md` §七「LLM 不參與任何判定」一致，是它的延伸——
規則的證據出處在整理時就已綁定，評估時照 ID 取回，那是一次 JOIN。

TFDA 藥品資料也比照辦理：事先匯出成藥名表（藥名 → 有效成分），系統評估時只查藥名表，不連 TFDA 資料庫。
組員電腦上的 TFDA 資料庫是產表工具，不放進展示用的系統。

「每次評估即時查外部來源」被拒絕的理由：

- **規則正確性無法驗證。** 每次結果取決於當下查到的資料，同一使用者兩次評估可能得到不同結論，
  也沒有一張固定的表可以覆核。
- **證據整合無法程式化。** 「一篇人體研究夠不夠」「仿單與論文矛盾怎麼辦」這類判斷
  寫成 Python 規則只會是假精確。典型例子：葉酸 × methotrexate 在文獻中是交互作用，
  但類風濕性關節炎治療常規會合併開立葉酸——自動整合會產生錯誤警示，只有人讀過原文才判斷得出來。
- **規模不符。** 當時估計藥物類別的規則約 20 條，為 20 條規則建五套即時 ETL 與證據分級引擎，
  工時與風險都不成比例。
- **外部依賴。** 任一來源服務中斷、改版或停止更新，評估結果就跟著變。
- **（2026-10-17 補充）藥名對照不需要即時查。** 第一版只問「這個藥名是哪個成分」，問法固定、範圍固定（16 類），
  展示也不需要最新資料，事先匯出的藥名表就涵蓋全部有效許可證。即時查 TFDA 會多出資料庫部署、
  確認流程與權限檢查，卻沒有多認得任何藥。

## Consequences

- 研究文件中「Evidence 怎樣才能進 Risk Engine」「Evidence Level 怎麼分」「紅黃藍怎麼定」
  三個問題，從**評估時的演算法**變成**建表規範（curation protocol）**：由人依規範判斷，把結果寫進表格欄位。
  建表規範必須在建表開工前定稿。
- 研究中盤點的各來源 schema **不需要成為產品資料庫的資料表**。
  產品只需要規則表、規則所引用的出處紀錄（見 `docs/schemas/rule-table.md`），以及藥名表。
- SUPP.AI 的角色是**整理規則時的查漏清單**：用來檢查有沒有漏掉某個候選交互作用，
  不是證據本身。它是以 NLP 從文獻自動擷取的句子，單獨不足以成立一條規則。
- 規則引擎本身變成確定性查表，其正確性以單元測試驗證；
  規則表的正確性則以雙人覆核與覆蓋率檢查驗證。
- 藥名表跟著快照版本走：快照之後才上市的新藥會被標成「無法確認」並在報告揭露。
- 任何讓系統在評估時呼叫外部來源的提案，都應視為推翻本 ADR，需重新決策。
